# Проверка видеотранспорта перед передачей через GitHub

Дата: 05.11.2026. Область: переносимость диагностического live и граница его поставки. Проверяющий не изменял рабочий код, не читал `private/`, `runtime/`, видео, действующие конфиги и токены, не обращался к камерам/облаку и не загружал сторонние библиотеки.

## Вывод

Кабинет можно передавать и запускать отдельно от Xiaomi live. Включённый в исходники мост **не является самодостаточным live-приёмником после clone**: ему нужны внешний Python helper, Python-пакеты, собранный Java-адаптер со сторонними `micam.*` классами, FFmpeg и приватная авторизация. Linux-работоспособность этого сочетания не проверена.

По умолчанию серверная поставка должна запускать только кабинет, с незаданным `PILOT_LIVE_CONFIG`. Включение одного диагностического live — отдельная настройка программистом после разрешения зависимостей и проверки прав на их использование. Наличие исходников и прежняя локальная проверка одного просмотра не подтверждают работу 24/7, всех камер или аналитики.

### Цепочка и внешние зависимости

`Node → Python bridge → Xiaomi HTTPS provisioning → Java relay (HEVC) → FFmpeg (H.264/fMP4) → авторизованный HTTP/MSE-плеер`.

Локальный API go2rtc используется отдельным CLI-путём `select_camera()` helper и не вызывается мостом. Нужен файл с ранее разрешённой авторизацией; процедура её получения/обновления на сервере остаётся отдельной задачей.

### Контракты путей

- `backend/live.mjs` принимает абсолютные существующие `command` и `cwd`; HTTP-пользователь не выбирает команду/аргументы. Процесс запускается с `shell:false`.
- Bridge требует абсолютные существующие `go2rtcConfig`, `java`, `ffmpeg`, `cloudTools`, `pythonDeps`, `privateRoot`. `javaClasses` — список абсолютных существующих **каталогов**, разделённых `os.pathsep`: на Linux это `:`, на Windows `;`. Прямой путь к JAR текущая проверка конфигурации не принимает.
- Название `pythonDeps` не устанавливает зависимости: этот каталог добавляется в `sys.path`. Надёжный путь — отдельное Linux-окружение с известным составом пакетов, а не копирование Windows site-packages.
- Путь bridge JSON и путь go2rtc YAML должны проходить через каталог с именем `private`; аналогичное требование действует для `privateRoot` и временного provisioning. Это условие именования, а не самостоятельная защита ОС: нужны права и изоляция файлов.
- В `RelayLive.java`/bridge/backend live нет зашитых абсолютных путей данного ПК. Перенос требует заново задать конфигурацию внутри Linux/контейнера, а не заменить букву диска в старом JSON.

### Реальное ограничение live в коде

Один активный просмотр на весь процесс, предел 600 секунд от создания билета, старт не более 110 секунд, контроль прекращения данных и прав. Java принимает только vendor 4 и поток HEVC/H.265; первый видеокадр должен быть ключевым. FFmpeg всегда удаляет аудио и задаёт 20 кадров/с. Настроенная возможность просмотра не доказывает доступность камеры. Другие модели, кодеки и vendor не подтверждены.

## Что включать в репозиторий

1. Оставить собственные текстовые исходники `tools/xiaomi_live_bridge.py`, `tools/RelayLive.java`, `backend/live.mjs`, связанные frontend/backend файлы и синтетические тесты. Они не содержат действующую конфигурацию и не запускают live сами по себе.
2. Для возможности воспроизвести optional bridge root перенёс в `tools/xiaomi_cloud_probe.py` копию helper из указанного родительского пути. В начале исходника сохранены ссылка на адаптированный go2rtc v1.9.15 и полный MIT copyright/license notice; его также описывает `NOTICE.md`. Наличие этого notice установлено по исходнику, актуальная внешняя проверка лицензии не проводилась.
3. Root добавил `tools/requirements-diagnostic.txt` с наблюдавшимися локальными версиями. Остаётся дополнить optional инструкцию способом сборки **нашего** `RelayLive.java` против отдельно разрешённого classpath и обезличенными примерами конфигурации, если программист решит включать live. Ни исходные Xiaomi ID/ключи, ни рабочий токен в примерах не нужны.
4. Включать Linux setup/build scripts только если они действительно подготовлены и проверены; этот отчёт не объявляет их существующими. Не делать скачивание внешнего transport условием сборки кабинета.

Перенос helper, `NOTICE.md` и список версий выполнены root и проверены по сохранённым текстовым файлам. Сборка transport и Linux установка пакетов остаются рекомендациями к optional поставке, а не проверенным результатом. Базовый кабинет можно передать без реализации этих рекомендаций, ясно указав отключённый live.

## Рекомендуемое отделение default от optional live

**Default:** Node/собранный frontend, собственный persistent data volume и синтетический/разрешённый реестр станций. `PILOT_LIVE_CONFIG` отсутствует; нет Python/Java/FFmpeg/vendor download, private Xiaomi mounts или сетевого подключения камер при старте. API явно сообщает `LIVE_NOT_CONFIGURED`/`not_connected`. Кнопка live не должна выглядеть как уже работающая камера. Полный Xiaomi-архив и короткий прежний клип не входят в default поставку.

**Optional diagnostic live:** отдельная инструкция/образ или отдельное Linux-окружение с явно разрешённым transport. Если используется текущий subprocess-контракт, все зависимости должны быть доступны тому же окружению, где Node запускает bridge: отдельный контейнер сам по себе этот контракт не соединяет. Выделение приёмника в другой сервис требует отдельного API-контракта и в этом handoff не реализовано.

Программист задаёт private `PILOT_LIVE_CONFIG`, создаёт один cameraId, проверяет Linux classpath/версии, доступ к токену и возможность записи временного provisioning. Файл go2rtc может быть read-only, `privateRoot` — узкий отдельный writable каталог. Нельзя монтировать весь исходный host runtime или home. Нужно проверить Stop/выход/отзыв прав/shutdown/таймауты, отсутствие ключей в ответах и логах, cleanup дочерних процессов и временных файлов на Linux. Для optional live reverse proxy требует отдельной настройки: пример `proxy_read_timeout 35s` кабинета не покрывает 110 секунд ожидания первого кадра; нужно достаточное ожидание и отключённая буферизация потока. Падение optional live не должно мешать входу и просмотру кабинета.

## Независимая проверка серверной поставки

После реализации другими исполнителями прочитаны `backend/config.mjs`, `security.mjs`, `store.mjs`, `server.mjs`, серверные изменения `app.mjs` и `tests/deployment.test.mjs`; `Dockerfile`, `compose.yaml`, `.dockerignore`, `.env.example`, `.github/workflows/ci.yml`, `package.json`, `deploy/healthcheck.mjs`, `database-backup.mjs`, `database-restore.mjs`, `container-smoke.sh`, `server-smoke.mjs`, `docs/SERVER_DEPLOYMENT.md`. Финальная smoke-проба использует `node:http`, чтобы передать Host как от reverse proxy; пароль обрабатывается с тем же удалением единственного завершающего перевода строки, что и startup config.

Установлено по исходникам:

- Server config проверяется до открытия SQLite и HTTP-порта; origin фиксирован, forwarded-заголовки не подменяют доверенную конфигурацию. Bootstrap пароль читается из отдельного файла, в сериализуемом config нет пароля/его хеша. Неканонический/небезопасный origin и неизвестная конфигурация отклоняются.
- В серверной пустой БД создаётся один новый администратор. Seed/demo БД отклоняется до миграций; известные demo-email для bootstrap запрещены. Cookie при входе и выходе имеет Secure; флаг demo-входа false.
- Нестрогого обхода `Host`/`Origin` в просмотренном коде не найдено. Исключение health ограничено GET `/api/health`, loopback Host, настоящим loopback socket и отсутствующим Origin.
- Первоначально найденная неограниченная `loginAttempts` Map исправлена backend-исполнителем: общий предел 120 запросов login в минуту на socket IP до разбора тела, 10 неудач на пару IP/email, TTL 60 секунд, максимум 1000 записей с отказом при заполнении. Подмена XFF не меняет peer IP. За reverse proxy общий IP-бюджет разделяется между пользователями; это ограничение, а не индивидуальный счётчик каждого клиента.
- Default runtime использует пользователя 1000:1000; Compose задаёт read-only rootfs, `cap_drop: ALL`, `no-new-privileges`, узкий data volume, tmpfs, memory/CPU/PID/log limits, публикацию только loopback и отдельную internal bridge network. Host network, privileged, Docker socket и системные host-каталоги в конфигурации отсутствуют.
- `.dockerignore` разрешает только нужные текстовые исходники/данные сборки; `tools`, `private`, `runtime`, локальные `node_modules` и медиа в build context не входят. Runtime не устанавливает диагностический видеотранспорт. CI проверяет/собирает без deploy и без обращения к инфраструктуре компании; права GitHub token — `contents: read`.

Проверяющим независимо выполнены: 13 синтетических assertions конфигурации/Origin/WeakMap без открытия сетевого порта — PASS; 3 целевых теста limiter — PASS; 2 теста backup/restore с временными SQLite/WAL — PASS. Эти проверки не читали рабочую БД или записи. Docker/Compose запуск на Linux данным проверяющим не выполнялся: Docker в текущем окружении отсутствует. Статический review не заменяет контейнерный CI и проверку HTTPS reverse proxy программистом. Блокирующих замечаний в просмотренной серверной дельте после исправления limiter не осталось.

## Неизвестное и приёмка

- Источник, лицензия, полный состав/target bytecode и поведение сторонних `micam.*` не установлены. Проверка адресов relay в нашем wrapper не заменяет аудит обработки пакетов transport-библиотекой.
- Linux сборка Java, реальный запуск pipeline, производительность транскодирования, долговечность токена и длительная устойчивость не проверены. Ограничения CPU/RAM кабинета нельзя считать измеренным бюджетом live.
- Фактический Docker/default режим на Linux, ограничения ресурсов в работе и внешний HTTPS проверяются CI/программистом после передачи; синтетические Node-тесты и review исходников не подтверждают работу всей инфраструктуры.
- Default приёмка: чистый clone собирается/стартует без камеры, Xiaomi-секретов и внешнего transport; login/RBAC и состояние «не подключён» работают. Optional приёмка: отдельный успешный Linux-просмотр, затем Stop/shutdown и подтверждённая очистка процессов/временных файлов. Даже этот результат не является приёмкой 24/7.
