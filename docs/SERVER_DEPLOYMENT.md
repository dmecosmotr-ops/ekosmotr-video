Для автоматического импорта приглашённых камер Xiaomi и ручного онлайн-просмотра предусмотрена отдельная опция установки. Инструкция — [XIAOMI_SHARED_CAMERAS.md](XIAOMI_SHARED_CAMERAS.md).

Подготовлена отдельная контейнерная поставка кабинета для проверки программистом. Она запускает интерфейс, права, журнал и SQLite. Видеоприёмник, реальный список камер, пробный MP4, Xiaomi-сессии и анализ видео в образ не входят. Без них кабинет работает, а просмотр показывает отсутствие подключённого источника. Это не подтверждение готовности 70 потоков или эксплуатации 24/7.

Команды ниже предназначены для Linux и Bash из корня отдельного репозитория `camera-pilot`. Они не выполняются автоматически на сервере компании. Docker и WSL на исходный Windows-ПК не устанавливались; локально Docker отсутствует. [GitHub CI](https://github.com/dmecosmotr-ops/ekosmotr-video/actions/runs/42001844023) уже подтвердил сборку и запуск образа на Linux. До внедрения нужна проверка программиста на площадке компании.

## Что согласовать перед запуском

| Параметр | Начальное значение / решение программиста |
| --- | --- |
| Docker | Поддерживаемый Docker Engine, не ниже 28, и Docker Compose v2 не ниже 2.24 |
| Внешний адрес | Отдельный HTTPS origin, например `https://cameras.company.ru`, без завершающего `/`, пути и параметров |
| Порт на сервере | `127.0.0.1:3210`; если занят, изменить только `PILOT_PUBLISHED_PORT` |
| Первый администратор | Корпоративный email и новый пароль в отдельном файле; пароль 16–200 символов |
| Ресурсы кабинета | 1 CPU, 512 MiB RAM, без swap, 64 процесса; это стартовые ограничения, не измеренный запас под нагрузку |
| Данные | Собственный именованный том `<compose-project>_pilot-data`, не каталоги соседних сервисов |
| Резервирование | Ответственный, частота, срок хранения и защищённое место вне этого тома; провести пробное восстановление |
| Видео | Отдельное решение после [проверки переносимости](VIDEO_DEPLOYMENT_REVIEW.md); базовый запуск его не требует |

Ограничения CPU/RAM действуют на работающий контейнер. Сборка frontend расходует дополнительные ресурсы. Объём БД и резервных копий не ограничен Compose: нужно контролировать свободный диск. Журналы Docker ограничены примерно 15 MiB, временный каталог — 16 MiB.

## Конфигурация и секрет первого входа

```bash
cp .env.example .env
mkdir -p deploy/secrets
chmod 700 deploy/secrets
umask 077
openssl rand -base64 36 > deploy/secrets/admin-password.txt
sudo chown 1000:1000 deploy/secrets/admin-password.txt
sudo chmod 400 deploy/secrets/admin-password.txt
```

Сохранить созданный пароль в принятом менеджере паролей. Не вставлять его в `.env`, Compose, Git, переписку или командную строку. Linux-контейнер работает как UID/GID `1000:1000`; файл должен быть читаем этим UID. В обычном Docker Compose файловые secrets сохраняют права исходного файла: параметры `uid/gid/mode` для такого источника не исправляют права автоматически. Защищённый каталог остаётся доступным владельцу и Docker; сам файл монтируется отдельно только для чтения. При rootless Docker программист должен отдельно проверить сопоставление UID и доступ к этому файлу. [Документация Docker о secrets](https://docs.docker.com/reference/compose-file/services/#secrets).

В `.env` задать реальный `PILOT_PUBLIC_ORIGIN`, `PILOT_ADMIN_EMAIL` и уникальный тег `PILOT_IMAGE`, например `ekosmotr-camera-pilot:review-<commit>`. Файл секретов, `.env` и резервные копии исключаются из Git и Docker context. Указанный путь к секрету обязателен при каждом запуске. Администратор создаётся только при пустой БД: замена файла не сбрасывает пароль существующего аккаунта. Серверный режим отвергает локальную БД с известными учебными аккаунтами; её нельзя переносить вместо нового тома.

## Сборка и запуск

```bash
docker compose config --quiet
docker compose build --pull
docker compose up --detach --no-build --wait --wait-timeout 90
docker compose ps
docker compose logs --tail 100 camera-pilot
docker compose exec -T camera-pilot node deploy/healthcheck.mjs
```

Сборка устанавливает frontend через `pnpm 10.28.2 install --frozen-lockfile`. Локальные `node_modules` и готовый `dist` не используются. Runtime содержит Node, backend, справочник станций, собранный frontend и инструменты резервирования; установка программ при запуске не выполняется. В образе нет Python, Java, FFmpeg, Xiaomi-конфигов и сторонних transport-классов. Служба не получает доступ к Docker socket, host network, системным каталогам и соседним томам.

Контейнер работает без root, с `read_only`, `cap_drop: ALL`, `no-new-privileges` и отдельной внутренней bridge-сетью. Писать можно в свой том данных и ограниченный временный каталог. Порт публикуется только на loopback сервера. Требование Docker Engine 28+ связано с исправлением доступа к опубликованным localhost-портам из той же локальной сети в более старых версиях. [Публикация портов Docker](https://docs.docker.com/engine/network/port-publishing/).

`GET /api/health` внутри контейнера проверяет работу HTTP-приложения, а не наличие видео, правильность прав всех пользователей или состояние инфраструктуры. Остальные запросы требуют правильного Host. Открытие HTTP-адреса `127.0.0.1:3210` в браузере не является способом серверного входа: используется согласованный HTTPS-домен и защищённая cookie.

## Домен и HTTPS

Настроить существующий reverse proxy компании на `http://127.0.0.1:3210`. Он завершает HTTPS и сохраняет исходный Host. Если выбран другой опубликованный порт, изменить upstream. Минимальный фрагмент для уже настроенного HTTPS `server` в Nginx:

```nginx
location / {
    proxy_pass http://127.0.0.1:3210;
    proxy_set_header Host $http_host;
    proxy_set_header Origin $http_origin;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_connect_timeout 5s;
    proxy_read_timeout 35s;
}
```

Это фрагмент, а не готовая настройка TLS, сертификатов, DNS и соседних сайтов. Приложение проверяет Host и Origin по точному `PILOT_PUBLIC_ORIGIN`; `X-Forwarded-*` не заменяют эту настройку. Не переписывать Origin на доверенное значение: иначе исчезнет проверка источника запроса. Кабинет рассчитан на корень отдельного домена; префикс наподобие `/cameras/` не проверялся.

Этот timeout подходит кабинету с отключённым видео. Если впоследствии отдельно разрешён диагностический live, ожидание первого кадра может достигать 110 секунд: потребуются другой timeout и отключение proxy buffering по [условиям видеоприёмника](VIDEO_DEPLOYMENT_REVIEW.md). Лимит 120 попыток входа в минуту применяется к адресу прямого соединения; за reverse proxy он общий для пользователей этого proxy, поскольку приложение не доверяет переданному `X-Forwarded-For`. Это нужно учесть при проверке одновременного входа.

После настройки открыть HTTPS-адрес: учебных кнопок входа быть не должно. Войти первым администратором, проверить список станций, создание ограниченного пользователя и его доступы, затем выйти. Без отдельного реестра камер не ожидать импортированных камер исходного ПК; отсутствие видео в этой поставке предусмотрено. Настоящий список и клип из `private/` автоматически не переносятся.

## Резервная копия и восстановление

Создать согласованную копию SQLite, включая зафиксированные данные WAL-журнала:

```bash
BACKUP_NAME=$(docker compose exec -T camera-pilot node deploy/database-backup.mjs)
mkdir -p backups
chmod 700 backups
docker compose cp "camera-pilot:/var/lib/camera-pilot/backups/$BACKUP_NAME" "./backups/$BACKUP_NAME"
chmod 600 "./backups/$BACKUP_NAME"
```

`VACUUM INTO` создаёт отдельный файл, затем выполняется проверка целостности. Копирование только рабочего `pilot.sqlite` без WAL во время работы не заменяет эту процедуру. Копию из `backups/` перенести в защищённое резервное хранилище компании; копия внутри того же Docker-тома не защищает от потери тома. Копия содержит пользователей, хеши паролей, сессии и журнал: не загружать её в Git, публичные CI-артефакты и внешние ИИ. Автоматическое расписание, шифрование, срок хранения и очистка копий в поставку не включены.

Восстановление выполнять при остановленном приложении. Выбрать имя нужной копии и версию образа, совместимую с ней:

```bash
docker compose stop camera-pilot
docker compose run --rm -T --no-deps \
  -e PILOT_RESTORE_CONFIRM=application-is-stopped \
  --entrypoint node camera-pilot deploy/database-restore.mjs < "./backups/$BACKUP_NAME"
docker compose up --detach --no-build --wait --wait-timeout 90
docker compose ps
```

Инструмент принимает один файл через stdin, проверяет SQLite и наличие таблиц приложения, затем сохраняет старые `pilot.sqlite`, WAL и SHM в каталоге `before-restore-*` того же тома. Ошибочный файл не должен заменять БД. Лимит входного файла — 1 GiB; большие БД требуют отдельного плана. Подтверждающий флаг сам не доказывает остановку: её обеспечивает предыдущая команда. После успешного восстановления заново проверить вход и права. Данные, появившиеся после даты копии, в восстановленной БД отсутствуют; старые файлы остаются для разбора ответственным.

## Обновление, остановка и откат

Перед обновлением записать текущий commit и `PILOT_IMAGE`, сделать копию выше. Для новой версии задать новый тег образа в `.env`, выполнить сборку, `docker compose up --detach --no-build --wait` и проверить HTTPS-вход. Сохранять прежний локальный образ и копию БД до приёмки. Ручной откат: вернуть прежний тег `PILOT_IMAGE`, при несовместимом изменении схемы восстановить соответствующую копию при остановленном приложении, затем запустить `up --no-build`. Обратная совместимость будущих миграций не обещается.

Штатная остановка: `docker compose stop camera-pilot`. Удаление контейнера без данных: `docker compose down`. Не использовать `down --volumes`/`down -v` на рабочей установке: эта команда удаляет её том. Только CI-smoke удаляет собственный временный проект и его синтетическую БД.

## CI и фактические границы проверки

Workflow `.github/workflows/ci.yml` проверяет состав поставки и признаки секретов через `tools/check-release.mjs`, выполняет Node-тесты backend/frontend/резервирования, Python-тесты диагностического моста без vendor transport, чистую установку из lockfile, frontend build, Docker build и запуск временного контейнера. Smoke проверяет health, отсутствие учебного входа, bootstrap-авторизацию, Secure-cookie, Origin, CSRF, выход и выключенное видео. CI имеет только `contents: read`; checkout не сохраняет Git credentials. В workflow нет deploy, SSH, push образа, инфраструктурных адресов или секретов компании.

Actions закреплены за проверенными полными commit SHA официальных релизов: [checkout v4.2.2](https://github.com/actions/checkout/commit/11bd71901bbe5b1630ceea73d27597364c9af683), [setup-node v4.4.0](https://github.com/actions/setup-node/commit/49933ea5288caeca8642d1e84afbd3f7d6820020), [setup-python v5.6.0](https://github.com/actions/setup-python/commit/a26af69be951a213d495a4c3e4e4022e16d87065).
