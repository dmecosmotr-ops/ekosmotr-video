# Онлайн-просмотр одной камеры — план реализации

**Goal:** по кнопке в локальном пилоте воспроизводится актуальное видео одной доступной Xiaomi-камеры, без ПК экспертов; остановка/закрытие просмотра освобождает видеосессию.
**Architecture:** существующая go2rtc-сессия → свежие параметры Xiaomi → ранее проверенный диагностический CS2-транспорт → FFmpeg HEVC/H.264 → fragmented MP4 через защищённый same-origin API → native video браузера. Если браузер не примет progressive fMP4, минимальный MSE-player без внешних зависимостей. Архивный MP4 источником live быть не может.
**Tech Stack:** существующие Node24/React; уже доступные Python/JDK21/FFmpeg и диагностические transport-классы. Новых платных сервисов, открытых портов, LAN-связей ПТО и публичного развёртывания нет.
**Spec:** текущий запрос владельца «в тестовом пилоте … онлайн режим рабочим»; прежние ограничения в CONTRACT.md и LIVE_VIDEO_RESULT.md.

## Контракт и ограничения

- Один видеосеанс на весь пилот; максимум 10 минут за запуск, явный stop, таймаут первого кадра, остановка при закрытии/отзыве доступа/выходе. Это диагностический пилот, не режим 24/7.
- В конфигурации сервера — только выбранный стабильный cameraId и фиксированная команда адаптера. DID/ключи/параметры находятся в private, не в URL/JSON/log/API/bundle. Нельзя запускать произвольные команды/источники через пользовательский ввод.
- GET /api/cameras/:id/playback: live={status:'available'|'not_connected',url:relative-or-null,message}. Available означает настроенную возможность запроса, не уже играющее видео.
- POST /api/cameras/:id/live (CSRF+Origin+canCamera) → {sessionId,streamUrl,stopUrl,expiresAt,maxDurationSeconds}; 503 if unconfigured, 409 if busy.
- GET /api/cameras/:id/live/:sessionId/stream → video/mp4, no-store; сессия привязана к пользователю и его login-session, повторное подключение отклоняется, чужой/несуществующий ресурс одинаково отрицается. Повторная проверка прав каждые ≤2с в ходе передачи.
- DELETE /api/cameras/:id/live/:sessionId (CSRF+Origin+current access) → {ok:true}; очистка handles и дочерних процессов. POST лишь создаёт короткий билет, subprocess запускается при GET; неиспользованный билет истекает быстро.
- Сервер проверяет no-first-byte/stall/max-lifetime, не выводит stderr внешних программ, не отдаёт секреты в ошибках. При остановке pipeline закрываются все дочерние процессы. После реальных нестабильных подключений: до авторизации видео разрешён один повтор relay-соединения (два отдельных socket, по30с); ожидание первого видео увеличено до110с. Это ограниченная проверка, не бесконечные фоновые подключения.
- Настроить только одну известную камеру по постоянному ID, имя/ПТО из текущего списка. Если адрес не подтверждён — так и показать. Никаких изменений настроек камер/прав Xiaomi/исходной Google-таблицы или аудио-MVP.
- Transport micam уже использовался только для диагностической пробы; явная лицензия и проверка отправителей UDP остаются ограничениями. Не включать vendor source в приложение, не заявлять production-готовность.

## Задачи и владельцы

1. Root — bridge: `tools/RelayLive.java`, `tools/xiaomi_live_bridge.py` в каталоге приложения; локальные private настройки/компиляция; fresh provisioning по исходному stable DID, контроль дочерних процессов, реальная проверка. Прежний RelayProbe не менять.
2. Backend-worker — только backend/live.mjs, app.mjs, playback.mjs, server.mjs и tests/live.test.mjs: билеты, права, stream/stop, лимиты, shutdown. Сначала meaningful failing HTTP/process tests, затем реализация.
3. Frontend-worker — только frontend: LivePlayer.jsx и VideoPanel.jsx/styles, старт/стоп/error/retry, cleanup на camera/mode/unmount, никакого автостарта всех камер/выдачи старого MP4 за live. Проверки жизненного цикла и сборка.
4. Независимый reviewer — read-only backend/bridge/frontend, без private/реальных камер. Проверка утечек/прав/cleanup/ошибок/актуальности вывода; root выполняет browser QA.
